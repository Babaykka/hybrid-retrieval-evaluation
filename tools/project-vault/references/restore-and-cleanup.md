# Транспорт, восстановление и освобождение места

## Перед загрузкой

Используй подходящий доступный connector/CLI; если его возможностей недостаточно, продолжай через поддерживаемый интерфейс. Не обходи блокировку доступа и не извлекай чужие сессии. Уже действующей авторизации достаточно для согласованного действия; не проси повторный вход без фактической необходимости.

Живьем проверь права канала, фактические лимиты клиента/API, доступный объем GitHub и выбранный способ загрузки. Не зашивай в навык меняющиеся лимиты размеров и тарифы. Сначала проверь транспорт на небольшом разрешенном файле; размер части оставь с запасом относительно доказанного лимита. Ссылка на сообщение или успешный вызов отправки сами по себе не доказывают сохранность байтов.

Разработка и все разрешенные результаты должны быть доступны через GitHub, включая большие файлы в Releases или другом согласованном механизме GitHub. Telegram хранит полное зеркало, а не единственную копию больших результатов. Для каждой стороны сверь полный состав; список внешних ссылок вместо результатов не считается полной копией, кроме явно согласованных upstream-источников.

При малом свободном месте:

- Пиши ограниченные части вне исходников с явным верхним пределом размера и резервом свободного места. Сжатие не гарантирует уменьшения; учитывай худший случай.
- Хешируй финальные байты каждой части при записи. Поток должен завершиться с проверенным кодом выхода; битая/усеченная часть не становится готовой при наличии имени.
- Удалять временную часть можно только после ее полного независимого чтения с удаленного сервиса и совпадения SHA-256. Это разрешение не распространяется на исходники.
- Для одного большого файла сначала загрузи и прочитай обратно все части, сохрани порядок, размеры и хеш полного собранного файла. Не создавай одновременно полный второй ZIP на переполненном диске.

Хранение полного проекта требует решения для всех его материалов. Если часть данных нельзя публиковать, явно зафиксируй ее отсутствие и не удаляй единственную локальную копию. Отдельный закрытый архив возможен только по согласованной схеме, вне репозиториев, если он содержит клиентские персональные данные.

## Устройство релиза и каталога

Основной пост с нейтральным ID содержит версию, дату, предмет, точный объем/число файлов, публичный manifest, ссылки на все части и GitHub, а также `RESTORE` с командами или простыми шагами. Запиши исходный метод упаковки и версии/зависимости, порядок частей, общий и частные хеши, ожидаемое дерево и команду значимой проверки результата. Сделай восстановление возможным на чистом компьютере без доступа к переписке.

Сохрани публичный каталог в том же канале/репозитории с нейтральными ID и постоянными ссылками. Закрепление или редактирование поста требует соответствующих прав; если их нет, создай связанный индекс в рамках разрешенной публикации и сообщи ограничение. После отправки прочитай пост и ссылки заново. Не считай канал полным резервным хранилищем без проверки доступности вложений.

Для поиска по имени клиента нужен отдельный зашифрованный каталог вне GitHub/Telegram. Его схема: нейтральный ID, приватный поисковый alias, ссылка основного поста, версия, manifest hash, расположение архива и инструкция доступа. Не печатай alias в публичных постах, логах CI, именах веток, коммитах и описаниях репозитория. Пользователь должен иметь доступ к ключу вне очищаемого ноутбука.

## Доказать восстановление

Проверка состоит из всех пунктов:

1. Полностью скачай каждую опубликованную часть через каждый сервис заново и сверь размер и SHA-256. Локальный файл, первоначально отправленный в сервис, не является readback.
2. Восстанови/распакуй весь набор в отдельное разрешенное хранилище. При нехватке места используй внешний диск/другую разрешенную машину; потоковая сверка доказывает байты, но не заменяет проверку восстановления, если файловая структура или инструмент распаковки еще не проверены.
3. Сверь фактическое дерево с публичным manifest: все файлы и размеры/хеши, отсутствие лишних неожиданных объектов, корректность относительных путей. Проверь границы архивов, контрольные суммы составных файлов и отсутствие небезопасных ссылок. Воспроизводимость преобразованной версии соотнеси с внутренней таблицей состава.
4. Открой ключевые документы, данные и результаты. Для кода запусти содержательную smoke-проверку/пример и запиши зависимости; не выполняй неизвестные программы только ради проверки архива.
5. Сохрани результат, время, версию, ссылки и hashes во внутреннем журнале. Публично укажи только реально пройденную проверку и известные ограничения. Проверь, что навык и инструкция восстановления также сохранены вне очищаемой папки.

## Удаление

Перед удалением перечисли точные одобренные пути и объем, проверь границы, ссылки, активные процессы/открытые файлы и соседние защищенные объекты по применимому workflow безопасного удаления. Используй имеющееся однозначное разрешение; при отсутствии такого разрешения запроси его для конкретного уже проверенного набора. Не создавай бессрочное разрешение этим навыком.

Нельзя удалять единственную копию непубличных исходников, исключенных файлов, приватного каталога или ключа. Если после обезличивания потерялась возможность восстановить исходный заказ, сообщи это до очистки: разрешенный публичный кейс и резервная копия оригинала являются разными результатами.

Удаляй только разрешенный набор, затем проверь отсутствие целей и сохранность соседних каталогов. В финале раздели: опубликовано; прочитано обратно; восстановлено и проверено; удалено локально; оставшиеся исключения. Не заявляй освобождение места до фактической проверки.
